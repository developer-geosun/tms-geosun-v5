## 1. Понимание

- Одно приложение и одна база. Предприятие — граница данных, не отдельный инстанс.
- Сотрудник принадлежит ровно одному предприятию. Вход: код + email + пароль. Тот же email в другой компании — другая учётка.
- Оператор платформы — отдельная учётка вне `users` и вне ролей `USER` / `MANAGER` / `DRIVER` / `ADMIN`. Свой вход, создание и приостановка предприятий, без операционных API.
- Свои данные: люди, автопарк, маршруты, фрахт, рейсы, файлы, бот, виды документов, сценарии и тарифы. Общие: страны, валюты, курсы НБУ, технический кэш геометрии HERE.
- Уже лежащие строки становятся первым предприятием. Код первого предприятия и оператор платформы обязательны в рабочем старте.
- Чужой id даёт 404. Клиент не присылает `enterpriseId` операционного объекта.
- Старый login без кода предприятия после релиза не работает. Уже выданные refresh-токены сотрудника доживают срок: пользователь после миграции уже в первом предприятии.

Одна ветка `feature/multi-enterprise`. Шаг не начинать, пока предыдущий компилируется и его тесты зелёные. Пакеты Java и SQL ниже — ориентир исполнителя, не второй источник истины рядом со спекой.

### 2.1. Схема и перенос

1. Flyway `V46__enterprises.sql`:
   - таблица `enterprises` (`id`, `name`, `code`, `active`, timestamps), уникальный `code`;
   - таблица `platform_operators` (`id`, `email`, `password_hash`, `active`, timestamps), уникальный email;
   - таблица refresh-токенов оператора по образцу `refresh_tokens` (свой hash, без смешения с токенами сотрудников);
   - `enterprise_id` NULL на корнях из таблицы в §3;
   - `trip_number_seq`: ключ с года на пару (предприятие, год) после переноса.
2. `EnterpriseBootstrapRunner` после Flyway, идемпотентно, в одной транзакции на перенос:
   - код и название первого предприятия из `app.enterprise.default-code` / `default-name`;
   - оператор из `app.bootstrap.platform-operator.email` / `password`;
   - пустые значения, слабый пароль или email оператора, совпавший с `users.email` либо с `ADMIN_EMAIL`, — ошибка старта рабочей среды, без секретов в логе;
   - все текущие корни и пользователи получают id первого предприятия; нынешние ADMIN остаются ADMIN этого предприятия;
   - повторный старт не создаёт второе предприятие и не меняет пароль оператора;
   - после нулевого числа NULL — `NOT NULL` и уникальные ключи из §3. Пока NULL остаются, рабочий старт неуспешен.
3. B19: `ADMIN_EMAIL` создаёт ADMIN первого предприятия, только если у этого предприятия ещё нет ADMIN. На базе, где ADMIN уже есть, bootstrap по-прежнему ничего не перезаписывает.
4. Тесты переноса: база со строками, пустая база, повторный старт, коллизия email оператора.

**Ход шага 2.1 (29 октября 2026):** код и миграция V46 есть. Два осознанных отступления от пунктов 1 и 2 выше, чтобы не разойтись с `ddl-auto=validate` и текущим `TripService`:

### 2.2. Вход и люди

5. Отдельный принципал оператора. JWT несёт вид принципала. Фильтр загружает либо сотрудника (роль и `enterpriseId` из БД, как роль сейчас), либо оператора. Старый токен без вида трактуется как сотрудник.
6. `LoginRequest`, `RegisterRequest`, `ForgotPasswordRequest`, `ResendVerificationRequest` получают `enterpriseCode`. В том же шаге обновить все вызовы в `src/main` и `src/test`, иначе сборка сломана.
7. Регистрация создаёт `USER` предприятия. Неизвестный или неактивный код — `400 ENTERPRISE_UNAVAILABLE`. Занятый в этом предприятии email или email оператора — `409`.
8. Login ищет пару (код, email). Чужой код и неверный пароль — один и тот же 401. Верный пароль при приостановке — `403 ENTERPRISE_SUSPENDED`.
9. `GET /auth/me` и ответы login/refresh добавляют `enterpriseCode`. Verify и reset остаются по токену.
10. Уникальность email: снять глобальный `uk_users_active_email`, поставить уникальность (`enterprise_id`, `active_email`) для неудалённых. Оператор в эту пару не входит, его email проверяется отдельно до вставки.
11. `/api/v1/admin/users` фильтруется предприятием вызывающего. `LAST_ADMIN_PROTECTED` считается внутри предприятия. `SUPER_ADMIN_PASSWORD` не становится паролем оператора.
12. API оператора из спеки §8.2: login, refresh, logout, список, создание с первым ADMIN (`emailVerified=true`), suspend/activate. Создание предприятия копирует каталог видов документов (шаг 18) и не копирует сценарии и тарифы.
13. `SecurityConfig`: `/api/v1/platform/**` только принципалу оператора. Операционный API оператору — `403 ENTERPRISE_SCOPE_REQUIRED`. Platform API сотруднику — `403 PLATFORM_SCOPE_REQUIRED`.

14. Порт текущего предприятия (id из принципала). Сервисы маршрутов, фрахта, рейсов, автопарка, файлов, бота и видов документов читают и пишут только его. `enterpriseId` в теле запроса игнорировать и не принимать как выбор компании.

16. Списки фильтруются в запросе к БД, не после полной выборки.
17. Уникальность внутри предприятия: `(enterprise_id, trip_number)`. Счётчик `trip_number_seq` — свой на предприятие и год; существующие значения года остаются у первого предприятия. `uk_trips_route_request` не трогать: id заявки глобальный. 18. Новое предприятие получает копию видов документов с канонических id `c2000000-…` (они остаются у первого предприятия, у копии новые id). Если первое предприятие уже правило эти строки, копия берёт их текущее содержимое. Отдельный неизменяемый шаблон вне предприятия спека не требует.

## 3. Затронутые модули

`enterprise_id` ставится на корень, у которого есть свой id в API. Дочерние строки живут через родителя: отдельная колонка им не нужна, пока их не отдают по собственному id без проверки родителя.

| Корень | Зачем колонка |
|--------|----------------|
| `users` | членство; уникальность email внутри предприятия |
| `vehicles`, `drivers`, `vehicle_combinations` | автопарк; документы ТС и водителя через родителя |
| `routes` | точки и разбивка по странам через маршрут |
| `route_requests` | история статусов через заявку |
| `freight_quotes` | котировка читается по своему id |
| `freight_numeric_scenarios`, `toll_tariff_sets` | правила toll через набор |
| `freight_cost_calculations` | расчёт по своему id |
| `trips` | номер уникален в предприятии; отчёт и строки затрат через рейс |
| `stored_files` | скачивание по id |
| `document_types` | свой каталог; копия при создании предприятия |
| `bot_identities`, `bot_link_codes` | привязка человека этого предприятия |

Без колонки предприятия: `country_reference`, `currencies`, `currency_nbu_rates`, `route_geometry_cache`, токены verify/reset (они указывают на user), `refresh_tokens` сотрудника.

| Модуль | Зачем |
|--------|--------|
| `auth` (user, JWT, admin users, bootstrap B19) | код входа, принципал, последний ADMIN внутри предприятия |
| `auth.notify` | получатели только своего предприятия |
| `platform` (новый пакет рядом с auth) | оператор, предприятия, запись стран и валют |
| `routes`, `freight.cost`, `trips`, `reference` (автопарк и виды документов), `storage`, `chatbot` | фильтр по id из порта, без импорта JPA `Enterprise` |
| `reference` страны и валюты | запись только оператору |
| `frontend-angular` login / register / forgot / auth.service / routes / navigation / i18n | код предприятия и кабинет оператора |
| `.env.example`, docker-compose, `RUN.ru.md` | обязательные переменные рабочего старта |

## 4. Риски и открытые вопросы

- Пропуск одного репозитория смешает компании. Приёмка бьёт прямым id, не только списком.
- Смена `LoginRequest` ломает все тесты входа разом. Их правят в том же шаге, что и DTO.
- `NOT NULL` после переноса: если runner упал посередине, повтор должен дописать NULL, а не создать второе предприятие.
- Копия каталога берёт текущие строки `c2000000-…`. Правки первого предприятия в этих карточках попадут новым компаниям. Отдельный замороженный шаблон в спеку не входит.
- Общий счётчик рейсов заменён на счётчик предприятия. Номера разных компаний могут совпасть; уникальность только внутри предприятия. Это соответствует спеке.
- Кэш геометрии общий. В ответе кэша не должно быть id маршрута чужой компании; при реализации это проверить и не класть такой id в ключ или тело.
- Старые клиенты без кода предприятия потеряют login в этот релиз. Refresh уже вошедших доживает срок.
- Продуктовых вопросов сверх спеки нет. Код не начинается без «+» на этот план.

## 5. Приёмка

Сверка с §13 спеки:

- два предприятия, прямой id чужого маршрута, рейса, файла и пользователя — 404;
- один email, два пароля, два кода;
- оператор создаёт предприятие и получает 403 на `/api/v1/admin/trips`;
- сотрудник получает 403 на `/api/v1/platform/enterprises`;
- приостановка гасит вход сотрудников и не гасит оператора;
- последний ADMIN защищён внутри своего предприятия;
- сотрудник не меняет валюту и страну; расчёт читает общий курс;
- новое предприятие имеет свою копию видов документов и пустые сценарии и тарифы;
- регистрация и новая заявка уведомляют только своих ADMIN;
- повторный старт не дублирует первое предприятие и не сбрасывает пароль оператора;
- пустой код или пустой оператор — рабочий старт неуспешен;
- Problems = 0 по §2.6.

Команды: тесты backend на новые срезы (`mvn -f backend-java/pom.xml test` с уже принятым в проекте отбором, либо полный прогон, если отбор не собирается); `npm --prefix frontend-angular run build`. UI кабинета и входа проверить в браузере на двух предприятиях до объявления шага 25 готовым.
