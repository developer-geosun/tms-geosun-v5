## 1) Goal / Цель

- **Problem / Проблема:** одно развёртывание — одно общее пространство. Вторая компания смешивает людей, автопарк, маршруты, фрахт, рейсы, файлы, бота и виды документов с первой. `ADMIN` видит всех.
- **Value / Ценность:** несколько независимых предприятий в одном приложении и одной базе. Чужие операционные данные не читаются и не меняются. Страны, валюты и курсы НБУ остаются общими.
- **Expected outcome / Ожидаемый результат:** сотрудник входит как «код предприятия + email + пароль» и видит только своё предприятие. Оператор платформы заводит предприятия и не работает диспетчером чужой компании. Уже накопленные строки становятся первым предприятием.

## 2) Context / Контекст

- **Project/module / Проект/модуль:** Angular + Java, модульный монолит. Новый поддерживающий контур Enterprise. Identity, Catalog, Storage, Notification и core (маршруты, фрахт, рейсы) получают границу `enterpriseId`. Flutter не входит.
- **Current behavior / Текущее поведение:** сущности предприятия нет. Email пользователя один на всё приложение. `POST /api/v1/auth/login`, `register`, `forgot-password`, `resend-verification` ищут учётку по email. Роли `USER`, `MANAGER`, `DRIVER`, `ADMIN` глобальные. Bootstrap `ADMIN_EMAIL` создаёт единственного ADMIN на пустую БД. Справочники стран и валют, сценарии фрахта, тарифы, виды документов, файлы, рейсы и бот не разделены. Уведомления ADMIN о регистрации и о новой заявке уходят всем ADMIN.
- **Related docs / Связанные документы:**
  - Brief: [multi-enterprise.ru.md](../briefs/multi-enterprise.ru.md)
  - Архитектура: [ddd-pragmatic.ru.md](../architecture/ddd-pragmatic.ru.md)
  - Канон, который эта фича сужает по видимости, не заменяя смысл ролей: B01 auth, B02 admin users, B03 profile, B04 notify registration, B05–B09 маршруты и фрахт, B11 files, B12–B13 автопарк, B14 рейсы, B15 виды документов, B16 chatbot, B18 multi-role, B19 bootstrap ADMIN, B20 notify freight request
  - Общие справочники без копии на предприятие: B10 валюты, B17 страны
- **Environment constraints / Ограничения окружения:** одна база, один процесс backend. Отдельный инстанс или отдельная схема на компанию не делаются.

## 3) Scope (In) / Scope (входит в задачу)

1. Предприятие: название, код для входа, признак «активно».
2. Одна учётка сотрудника — ровно одно предприятие. Набор ролей и активная роль не меняют смысл (B18), меняется только область видимости.
3. Email уникален внутри предприятия. Тот же адрес в другом предприятии — другая учётка, свой пароль и свои роли.
4. Вход, регистрация, повтор письма верификации и запрос сброса пароля сотрудника требуют код предприятия.
5. Оператор платформы: учётка вне предприятий, отдельный вход без кода предприятия, создание и приостановка предприятий, первый ADMIN нового предприятия.
6. Уже существующие операционные строки и пользователи переносятся в первое предприятие. Появляется обязательный оператор платформы.
7. Граница на сервере у всех операционных данных: люди, автопарк, маршруты и точки, заявки, котировки, сценарии и тарифы, расчёты, рейсы и отчёты, файлы, привязки бота, каталог видов документов.
8. Общие данные платформы: страны, валюты, курсы НБУ. Запись в них — только оператор платформы. Чтение курсов расчётом фрахта — как сейчас, одна копия на всех.
9. Новое предприятие получает свою копию каталога видов документов UA (набор B15). Сценарии себестоимости и тарифы toll не копируются: у новой компании они пустые.
10. Уведомления ADMIN о регистрации и о новой заявке на фрахт получают только ADMIN того же предприятия.
11. Рабочие экраны Angular (Material): код предприятия на входе сотрудника; отдельный вход и минимальный кабинет оператора платформы.

## 4) Out of Scope / Out of Scope (не входит)

- Членство одной учётки в нескольких предприятиях и переключатель предприятия в сессии.
- Один email как одна учётка на всю платформу.
- Свой домен, белая метка, биллинг платформы.
- Заявка или рейс сразу на два предприятия.
- Свои курсы, свои валюты или свой справочник стран у предприятия.
- Общий живой каталог видов документов на все предприятия.
- Отдельная установка или отдельная база на предприятие.
- Новые роли внутри предприятия и отдельный Telegram-бот на предприятие. Токен бота в окружении остаётся один на развёртывание; данные привязок делятся по предприятию.
- Удаление предприятия и перенос строк между предприятиями.
- Визуальный порт 24 этапов редизайна. Эта фича не ждёт приёмку App Shell.
- Flutter.

## 5) User Stories / Пользовательские сценарии

1. **Как** сотрудник, **я хочу** войти по коду предприятия, email и паролю, **чтобы** открыть только свою компанию.
2. **Как** человек с тем же email во второй компании, **я хочу** отдельную учётку, **чтобы** пароль и роли не были общими с первой.
3. **Как** оператор платформы, **я хочу** создать предприятие и его первого администратора, **чтобы** вторая компания начала работу без доступа к данным первой.
4. **Как** администратор предприятия, **я хочу** видеть и менять только своих людей, машины, маршруты, заявки, рейсы, файлы, бота и виды документов.
5. **Как** водитель, **я хочу** видеть только свои рейсы своего предприятия.
6. **Как** владелец уже работающей базы, **я хочу** сохранить текущие данные первым предприятием и войти в него известным кодом.

## 6) Functional Requirements / Функциональные требования

### Предприятие

1. Предприятие хранит id, название (1–200 символов), код и флаг активности. Код: 2–32 символа, латиница в нижнем регистре, цифры и дефис, уникален без учёта регистра, не равен зарезервированному `platform`. В API и в формах код нормализуется в нижний регистр до проверки.
2. Клиент не передаёт `enterpriseId` в телах создания маршрута, рейса, ТС, файла и остальных операционных объектов. Сервер подставляет предприятие текущего сотрудника. Чужой id в пути или в теле не расширяет доступ.
3. Объект другого предприятия по id отвечает **404**, как отсутствующий. Нельзя отличить «нет» от «чужое».
4. Приостановленное предприятие: верный пароль сотрудника даёт **403** `ENTERPRISE_SUSPENDED`. Неверный пароль по-прежнему **401**, без отдельного сигнала, что код предприятия существует. Оператор платформы входит независимо от этого флага.
5. Удаление предприятия в v1 нет. Приостановка и возврат в активное состояние — есть, только оператором платформы.

### Учётки сотрудников

6. Учётка сотрудника обязана иметь ровно одно предприятие. Сменить предприятие существующей учётке в v1 нельзя.
7. Пара (предприятие, email) уникальна среди неудалённых учёток. Регистр email не создаёт вторую пару: нормализация как сейчас.
8. Email оператора платформы не может совпасть ни с одним email сотрудника и ни с каким будущим email сотрудника. Занятый адрес отклоняется и при создании оператора, и при регистрации или заведении пользователя.
9. `POST /api/v1/auth/register` создаёт `USER` в предприятии по коду. Неизвестный или приостановленный код — **400** `ENTERPRISE_UNAVAILABLE` (не различать «нет» и «приостановлено»). Email уже занят в этом предприятии — **409**, как сейчас для занятого email. Роль по умолчанию — `USER` этого предприятия.
10. `POST /api/v1/auth/login` ищет учётку по паре (код, email). Неверная пара или пароль — **401** одной и той же ошибкой. Дальше действуют текущие правила B01: неподтверждённый email, отключённая и удалённая учётка.
11. `POST /api/v1/auth/forgot-password` и повторная отправка письма верификации требуют код предприятия. Ответ при неизвестной паре — тот же успех, что и сейчас при неизвестном email (anti-enumeration). Письмо уходит только учётке этой пары.
12. `verify-email` и `reset-password` остаются по токену. Токен уже указывает на конкретную учётку; код предприятия в этих запросах не нужен.
13. `switch-role` меняет только активную роль этой учётки (B18). Роль другого предприятия выдать нельзя.
14. Списки и карточки `/api/v1/admin/users` ограничены предприятием вызывающего. `MANAGER` читает, мутации — только `ADMIN` своего предприятия (B02). `LAST_ADMIN_PROTECTED` считается внутри предприятия: последнего активного ADMIN этой компании снять нельзя. `SUPER_ADMIN_PASSWORD` остаётся step-up для опасных операций с ADMIN, это не пароль оператора платформы.
15. Саморегистрация и создание пользователя администратором не принимают роль платформы и не оставляют учётку без предприятия.

### Оператор платформы

16. Оператор не состоит в предприятии и не имеет ролей `USER` / `MANAGER` / `DRIVER` / `ADMIN`. Его принципал не проходит проверки `hasRole` этих ролей и не открывает операционные API.
17. Вход оператора — отдельный запрос, только email и пароль. Код предприятия не принимается.
18. Оператор создаёт предприятие: название, код, email и пароль первого ADMIN. Первый ADMIN: роль `ADMIN`, `emailVerified = true`, активен, пароль по тем же правилам, что регистрация (≥8, буква и цифра).
19. Оператор видит список предприятий (название, код, активность) и может приостановить или вернуть предприятие. Операционные списки (маршруты, рейсы, люди, файлы) ему недоступны.
20. Сотрудник, вызвавший API оператора, получает **403**.

### Данные

21. К предприятию относятся: пользователи и роли, ТС, водители, автопоезда и их документы, маршруты и точки, заявки, котировки, сценарии себестоимости, тарифы toll, расчёты фрахта, рейсы и отчёты о затратах, файлы, привязки и коды бота, виды документов.
22. Страны, валюты и курсы НБУ — одна копия на платформу. Синхронизация НБУ остаётся одной задачей на развёртывание. Менять страны и валюты может только оператор платформы. `ADMIN` и `MANAGER` предприятия эту запись теряют. Расчёт ставки читает общие курсы, как B08/B10.
23. При создании предприятия сервер копирует в него каталог видов документов UA (актуальный набор B15, UUID вида `c2000000-…` как источник состава, у копии новые id). Существующие строки каталога при миграции остаются у первого предприятия и второй раз не клонируются.
24. Сценарии и тарифы нового предприятия пустые.
25. Номер рейса, ключи идемпотентности и прочие уникальные бизнес-номера, сегодня уникальные на всю базу, становятся уникальными внутри предприятия. Полный перечень ограничений — в плане реализации; правило здесь обязательное.
26. Внешний id мессенджера (учётная запись Telegram и аналоги) уникален на всю платформу: один внешний аккаунт — одна учётка. Повторная привязка к пользователю другого предприятия отклоняется.
27. Уведомление о новой регистрации (B04) и о новой заявке на фрахт (B20) получают активные ADMIN **этого** предприятия, у которых роль ADMIN есть в available. ADMIN других предприятий получателями не являются.

### Уже существующая база

28. Если в базе есть пользователи или операционные строки без предприятия, старт рабочей среды выполняет перенос в первое предприятие и без успешного переноса не считается готовым.
29. Код и название первого предприятия задаются конфигурацией окружения. Пустой код — ошибка старта, молчаливый код не подставляется. Все текущие пользователи, включая нынешних `ADMIN`, становятся участниками этого предприятия. Нынешний `ADMIN` остаётся администратором предприятия, а не оператором платформы.
30. Оператор платформы создаётся из отдельной пары email/пароль в окружении, если такого оператора ещё нет. Пустая пара, слабый пароль или email, совпавший с уже существующим пользователем, — ошибка старта рабочей среды. Пароль в лог не пишется.
31. Повторный старт не создаёт второе «первое» предприятие, не дублирует перенос и не перезаписывает пароль оператора.
32. Пустая база: создаётся первое предприятие из той же конфигурации, bootstrap `ADMIN_EMAIL` / `ADMIN_PASSWORD` (B19) создаёт ADMIN **этого** предприятия, если своего ADMIN у него ещё нет, и отдельно создаётся оператор платформы. Email bootstrap-ADMIN и email оператора обязаны различаться; иначе старт рабочей среды завершается ошибкой.
33. Тестовый контекст может создать предприятие и оператора фикстурой. Требование «ошибка старта без оператора» относится к рабочему запуску, не к unit-тестам без этой фикстуры.

## 7) Non-functional Requirements / Нефункциональные требования

- **Security / Безопасность:** граница предприятия проверяется на сервере при каждом чтении и записи. Скрытие пункта меню её не заменяет. `enterpriseId` не принимается от клиента как способ выбрать чужую компанию. Пароли и токены в логи не пишутся. Перебор входа не сообщает, существует ли код предприятия.
- **Performance / Производительность:** списки операционных данных фильтруются по предприятию в запросе к БД, не в памяти после выборки всей таблицы.
- **Reliability / Надежность:** перенос существующих строк и создание первого предприятия идемпотентны при повторном старте.
- **Logging/Monitoring / Логирование и мониторинг:** старт фиксирует создание первого предприятия и оператора без секретов и без списка чужих email. Отказ доступа к чужому id логируется как отказ без тела чужого объекта.
- **Accessibility/UX / Доступность и UX:** новые поля — компоненты Angular Material. Подписи входа — в существующие файлы локалей `uk` / `en` / `ru`. Отдельный `ua.json` не заводить.

## 8) Data Contracts and API / Контракты данных и API

Существующие пути операционных API не меняются. Меняется область данных и тела тех запросов, где email больше не однозначен. Ниже — только новые и изменённые контракты.

### 8.1 Сотрудник

- `POST /api/v1/auth/login`

```json
{ "enterpriseCode": "geosun", "email": "user@example.com", "password": "string" }
```

Ответ 200 — как B01 (`accessToken`, `refreshToken`, `user`). В `user` добавляется `enterpriseCode`. Поле `role` по-прежнему активная роль.

- `POST /api/v1/auth/register` — к текущему телу добавляется обязательный `enterpriseCode`. Учётка создаётся в этом предприятии.
- `POST /api/v1/auth/forgot-password` и повтор верификации — обязательный `enterpriseCode` рядом с `email`.
- `GET /api/v1/auth/me` и ответ `refresh` — в объект пользователя добавляется `enterpriseCode`.
- `POST /api/v1/auth/verify-email`, `reset-password`, `logout`, `switch-role` — тела без кода предприятия.

Ошибки сотрудника:

| Код | HTTP | Когда |
|-----|------|--------|
| неверные учётные данные (тот же код, что login B01) | 401 | нет пары код+email, неверный пароль |
| `ENTERPRISE_SUSPENDED` | 403 | пароль верен, предприятие приостановлено |
| `ENTERPRISE_UNAVAILABLE` | 400 | регистрация: код неизвестен или предприятие неактивно |
| `EMAIL_TAKEN` | 409 | email уже есть в этом предприятии или совпал с оператором платформы |
| `PLATFORM_SCOPE_REQUIRED` | 403 | сотрудник вызвал API оператора |

Остальные коды B01 (`ACCOUNT_DISABLED`, `USER_DELETED`, неподтверждённый email) сохраняются.

### 8.2 Оператор платформы

- `POST /api/v1/platform/auth/login`

```json
{ "email": "operator@example.com", "password": "string" }
```

Ответ 200: `accessToken`, `refreshToken`, `tokenType`, `expiresIn`, объект оператора (`id`, `email`) без `role` сотрудника и без `enterpriseCode`.

- `POST /api/v1/platform/auth/refresh` — новое обновление токена оператора. Refresh сотрудника сюда не подходит.
- `POST /api/v1/platform/auth/logout` — завершение сессии оператора.
- `GET /api/v1/platform/enterprises` — список: `id`, `name`, `code`, `active`.
- `POST /api/v1/platform/enterprises`

```json
{
  "name": "Second Carrier",
  "code": "second",
  "adminEmail": "admin@second.example",
  "adminPassword": "string"
}
```

Ответ 201: предприятие и `adminUserId`. Пароль в ответе не возвращается.

- `POST /api/v1/platform/enterprises/{id}/suspend` и `POST /api/v1/platform/enterprises/{id}/activate` — смена флага. Идемпотентны.

Ошибки оператора: **401** при неверном входе; **409** при занятом коде предприятия или email первого ADMIN; **400** при невалидном коде или слабом пароле; **403** `ENTERPRISE_SCOPE_REQUIRED`, если оператор вызвал операционный API сотрудника.

### 8.3 Что не меняется по пути

Чтение и запись маршрутов, фрахта, рейсов, автопарка, файлов, бота, видов документов, сценариев и тарифов остаются на текущих URL и ролях. Сервер ограничивает их предприятием принципала. Запись стран и валют с ролей предприятия снимается и доступна оператору платформы отдельными операциями кабинета платформы; контракт полей справочника остаётся контрактом B10 и текущего справочника стран.

## 9) UX/UI Requirements (frontend) / UX/UI требования (frontend)

- Вход, регистрация, «забыли пароль» и повтор верификации: поле кода предприятия перед email. Пустой код не отправляется.

## 10) Architecture Changes / Изменения в архитектуре

- **Контекст:** Enterprise — supporting, не core. Core-агрегаты (маршрут, заявка и ставка, рейс) не импортируют JPA-сущность предприятия и его repository. Они хранят id предприятия и получают его из порта текущего принципала.
- **Identity:** членство «учётка → одно предприятие» живёт рядом с пользователем. Оператор платформы — отдельный принципал, не роль в `Role` сотрудника.
- **Запись:** application service загружает принципала, берёт `enterpriseId`, вызывает доменную операцию, сохраняет. Подменить предприятие сеттером из чужого сервиса или полем DTO нельзя.
- **Catalog:** страны, валюты и курсы НБУ остаются без `enterpriseId`. Виды документов, сценарии и тарифы — с `enterpriseId`.
- **Storage и Notification:** файл и привязка бота принадлежат предприятию владельца. Рассылка ADMIN фильтруется этим id.
- **Совместимость:** старые клиенты, шлющие login без `enterpriseCode`, перестают входить. Это осознанный разрыв контракта B01 в момент включения фичи, не параллельный «режим без предприятия».
- План реализации перечисляет таблицы и уникальные ограничения. В этой спеке пакеты Java и SQL миграций не фиксируются.

## 14) Test Plan / Тест-план

- **Unit:** нормализация и запрет кода `platform`; инвариант «учётка без предприятия запрещена»; подсчёт последнего ADMIN внутри одного предприятия.

## 15) Risks and Assumptions / Риски и допущения

- **Risks / Риски:** пропуск фильтра в одном репозитории смешает компании. Поэтому приёмка включает чужой id, а не только список. Старые клиенты без кода предприятия потеряют вход в релиз этой фичи.
- **Assumptions / Допущения:** владельцу известен код первого предприятия до включения на рабочей базе. Один токен бота на развёртывание достаточен. Копия каталога UA нужна каждой новой компании; коммерческие сценарии и тарифы — нет.
- **Rollback plan / План отката:** до выкладки на рабочую базу — откат миграции вместе с релизом. После переноса строк обратное «общее пространство» отдельным скриптом в этой спеке не обещается: возврат только восстановлением резервной копии, снятой до старта версии.
